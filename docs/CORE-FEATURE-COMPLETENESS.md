# 핵심·기본 기능 완성도 평가 기준

## 1. 목적과 판정 원칙

이 문서는 “코드가 있다”가 아니라 **대상 사용자가 의도한 결과를 신뢰성 있게 얻을 수 있는가**를 측정하기 위한 리뷰 기준선이다. 핵심 기능 리뷰 시 참고하되, 최종 판단은 실제 코드·실행 결과·제품 맥락을 종합한 Codex의 독립 판단을 우선한다.

다음 원칙은 점수보다 우선한다.

1. 기능은 화면이나 파일 단위가 아니라 사용자가 얻는 결과 단위로 정의한다.
2. `TODO.md`의 체크, 코드 존재, 빌드 성공, 테스트 개수는 보조 증거일 뿐 완료 증거가 아니다.
3. 확인하지 않은 것은 통과가 아니라 `미확인`이다. 미확인 항목에는 점수를 주지 않는다.
4. 높은 평균 점수가 치명적인 한 기능의 실패를 가릴 수 없다. 필수 게이트와 최약 기능을 별도로 판정한다.
5. 정상 경로뿐 아니라 실패 감지, 데이터 보존, 복구 가능성까지 동작해야 한다.
6. 자동화된 근거와 실제 사용자 가치가 충돌하면 실제 관찰을 우선하고 원인을 조사한다.
7. 이 기준과 Codex의 전문 판단이 충돌하면 Codex의 판단을 우선하되, 무엇을 왜 다르게 판단했는지 리뷰에 기록한다.

## 2. 평가 대상을 먼저 고정한다

리뷰 전에 아래 내용을 한 문장씩 작성한다. 이를 작성하지 못하면 점수도 산출하지 않는다.

- **대상 사용자:** 누가 사용하는가?
- **사용자 결과:** 어떤 작업을 끝내거나 어떤 결정을 내릴 수 있어야 하는가?
- **시작·종료 상태:** 무엇을 가진 상태에서 시작해 어떤 확인 가능한 상태로 끝나는가?
- **지원 범위:** 지원하는 입력, 환경, 데이터 크기와 명시적으로 지원하지 않는 범위는 무엇인가?
- **실패 비용:** 실패 시 데이터 손실, 잘못된 의사결정, 작업 지연 등 영향은 무엇인가?
- **리뷰 기준점:** 커밋, 날짜, 실행 환경, 관련 요구사항 또는 사용자 약속은 무엇인가?

기능 분류는 다음 질문으로 결정한다.

| 분류              | 판별 질문                                                                                                  | 이 프로젝트에서 가능한 예시                                      |
| ----------------- | ---------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| 핵심(Core)        | 이것이 실패하면 제품의 주된 사용자 약속이나 핵심 여정을 달성할 수 없는가?                                  | 도면 생성·불러오기, 2D 보정, 일관된 3D 변환, 실측 가구 배치·수정 |
| 기본(Basic)       | 주된 차별점은 아니지만 정상적인 제품이라면 사용자가 당연히 기대하며, 없으면 핵심 여정의 신뢰가 무너지는가? | 저장·재열기, Undo/Redo, 오류 안내, 내보내기, 기본 접근성·호환성  |
| 확장(Enhancement) | 없어도 약속한 핵심 결과와 기본 신뢰성을 달성할 수 있는가?                                                  | 편의 프리셋, 장식적 효과, 아직 약속하지 않은 고급 기능           |

분류는 현재 구현량이 아니라 제품 약속과 실패 영향으로 정한다. README, UI 문구, 사용자 시나리오가 자동 변환을 주된 약속으로 제시한다면 해당 경로를 구현이 불안정하다는 이유로 확장 기능으로 낮출 수 없다. 한 기능이 핵심과 기본 역할을 동시에 하면 더 높은 위험 등급인 핵심으로 취급한다.

## 3. 기능별 수용 계약

각 핵심·기본 기능은 평가 전에 다음 수용 계약을 가져야 한다.

| 항목          | 반드시 답할 내용                                                     |
| ------------- | -------------------------------------------------------------------- |
| 결과          | 사용자가 관찰할 수 있는 성공 상태                                    |
| 정상 경로     | 시작부터 결과까지 끊기지 않는 단계                                   |
| 경계값        | 빈 값, 최소·최대, 큰 데이터, 중복 입력 등                            |
| 실패·복구     | 오류 감지, 설명, 재시도·취소·원복 방법                               |
| 데이터 불변식 | 단위, 좌표, ID, 저장·불러오기 후 보존돼야 할 값                      |
| 품질 문턱     | 정확도, 지연, 호환성, 접근성 등 측정 가능한 한계                     |
| 증거          | 어떤 명령, 테스트, 데이터, 스크린샷 또는 관찰이 각 조건을 입증하는지 |

“잘 동작한다”, “사용하기 쉽다”처럼 관찰하거나 반증할 수 없는 조건은 인정하지 않는다. 품질 문턱은 결과를 본 뒤 유리하게 바꾸지 말고 평가 전에 정한다.

## 4. 필수 게이트: 하나라도 실패하면 완료가 아니다

점수를 계산하기 전에 아래 게이트를 확인한다.

### 모든 핵심 기능

- 약속된 정상 경로를 실제 실행 환경에서 처음부터 끝까지 완료할 수 있다.
- 성공처럼 보이지만 결과가 틀리는 조용한 실패를 감지하거나 사용자에게 한계를 명확히 표시한다.
- 실패·취소·재시도 후 상태가 손상되지 않으며 사용자가 복구할 수 있다.
- 저장, 불러오기, Undo/Redo 또는 변환 경계를 지날 때 핵심 데이터 불변식이 유지된다.
- 해결되지 않은 P0(데이터 손실·보안·핵심 여정 불능) 또는 P1(일반 조건의 중대한 오동작)이 없다.
- 주장하는 지원 환경과 대표 입력에서 재현 가능한 증거가 있다.

### 모든 기본 기능

- 핵심 여정에서 실제로 연결되어 있고 자리표시자, 죽은 버튼, 무응답 상태가 아니다.
- 오류와 진행 상태가 사용자가 이해할 수 있게 표시된다.
- 핵심 작업을 막는 키보드·포커스·가시성·호환성 문제가 없다.
- 관련 핵심 데이터에 손실이나 예기치 않은 덮어쓰기를 만들지 않는다.

게이트 실패 기능은 점수와 무관하게 `미완료`다. 미확인 게이트도 완료 선언을 차단하지만, 실제 결함과 증거 부족을 구분해 `미확인`으로 기록한다. 단, 지원 범위 밖임이 제품에 명확히 표시되고 핵심 약속을 훼손하지 않는 경우에는 그 근거를 기록하고 제외할 수 있다.

## 5. 점수와 증거 강도

### 5.1 품질 차원

각 기능을 아래 7개 차원에서 0~4점으로 평가한다.

| 차원           | 가중치 | 질문                                                                  |
| -------------- | -----: | --------------------------------------------------------------------- |
| 결과 정확성    |     30 | 산출물이 수용 계약과 데이터 불변식을 만족하는가?                      |
| 전 과정 연결성 |     20 | 실제 UI/API 경로가 처음부터 끝까지 끊김 없이 이어지는가?              |
| 경계·오류·복구 |     15 | 경계 조건과 의존성 실패를 안전하고 이해 가능하게 처리하는가?          |
| 데이터 신뢰성  |     10 | 저장·재열기·Undo/Redo·내보내기·마이그레이션 후 값이 보존되는가?       |
| 사용성·접근성  |     10 | 대상 사용자가 과도한 추측이나 숨은 조작 없이 완료할 수 있는가?        |
| 성능·호환성    |     10 | 약속한 데이터 크기와 환경에서 응답성·렌더링·호환성이 문턱을 넘는가?   |
| 운영·보안·준수 |      5 | 오류 관찰, 민감정보, 외부 의존성, 라이선스 등 출시 위험이 통제되는가? |

점수 의미:

- `0`: 없거나 실행 불가, 또는 미확인
- `1`: 데모 일부만 가능하며 일반적인 사용에 실패
- `2`: 대표 정상 경로는 가능하지만 중요한 누락·수동 우회가 있음
- `3`: 약속 범위에서 안정적이며 알려진 제한이 경미하고 명확함
- `4`: 대표·경계·실패 조건까지 반복 검증되어 출시 판단에 충분함

적용되지 않는 차원은 근거와 함께 `N/A`로 제외하고 나머지 가중치를 비례 재분배한다. 점수를 올리기 위한 자의적 N/A 처리는 허용하지 않는다.

### 5.2 증거 수준

각 차원 점수에는 그 주장을 직접 입증하는 증거 수준을 붙인다.

| 수준 | 계수 | 인정되는 증거                                                     |
| ---- | ---: | ----------------------------------------------------------------- |
| E0   | 0.00 | 주장, 체크박스, 실행하지 않은 추정, 현재 코드 존재만 확인         |
| E1   | 0.55 | 타입 검사·빌드·정적 분석, 제한된 수동 코드 검토                   |
| E2   | 0.75 | 결정론적 단위·통합 테스트, 계약·불변식 검증                       |
| E3   | 0.90 | 실제 브라우저/런타임의 전체 경로 검증, 시각 결과와 오류 상태 확인 |
| E4   | 1.00 | 대표 실데이터·지원 환경의 반복 검증 또는 대상 사용자 관찰         |

증거는 주장에 맞아야 한다. 예를 들어 단위 테스트는 시각적 3D 완성도를, DOM 존재 검사는 WebGL 렌더 성공을, 한 장의 성공 사례는 CV 일반 정확도를 입증하지 않는다. 여러 증거가 있으면 해당 차원을 직접 검증한 가장 강한 증거를 쓰되, 낮은 수준의 반증을 숨기지 않는다.

기능의 유효 점수는 다음과 같다.

```text
유효 점수 = Σ(차원 가중치 × 차원 점수 / 4 × 해당 증거 계수)
```

예를 들어 결과 정확성이 3점이고 근거가 E2뿐이면 `30 × 3/4 × 0.75 = 16.875점`이다. 테스트를 실행하지 않았거나 결과를 확인할 수 없으면 E0이므로 그 차원은 0점이며 `미확인` 사유를 함께 남긴다.

### 5.3 기능 상태

| 상태             | 조건                                                                         |
| ---------------- | ---------------------------------------------------------------------------- |
| 미완료           | 필수 게이트 실패 또는 유효 점수 50 미만                                      |
| 부분 구현        | 게이트 통과, 50~69점                                                         |
| 제한적 사용 가능 | 게이트 통과, 70~84점. 제한과 우회 방법을 사용자에게 표시해야 함              |
| 완료 후보        | 게이트 통과, 85점 이상, 어떤 차원도 원점수 2 미만이 아님                     |
| 검증 완료        | 완료 후보 조건 + 90점 이상 + 전 과정 E3 + 위험에 맞는 E4 + 미해결 P0/P1 없음 |

`완료 후보`는 코드·제품 리뷰를 통과할 가능성이 높다는 뜻이지 실제 사용자 가치가 입증됐다는 뜻은 아니다. 외부 출시나 “완성” 주장은 `검증 완료`를 기본 문턱으로 한다.

## 6. 전체 완성도 집계

핵심과 기본 기능은 섞지 않고 각각 보고한다.

```text
핵심 완성도 지수 = Σ(핵심 기능 유효 점수 × 기능 중요도) / Σ기능 중요도
기본 완성도 지수 = Σ(기본 기능 유효 점수 × 기능 중요도) / Σ기능 중요도
```

기능 중요도는 `1~3`으로 수용 계약 전에 정한다. 구현 결과를 본 뒤 가중치를 바꾸지 않는다.

평균과 함께 반드시 다음을 제시한다.

- 가장 낮은 핵심 기능 점수와 상태
- 실패한 게이트 수
- E3 이상으로 검증된 핵심 기능 비율
- 미확인 항목 수와 그 영향
- P0/P1 결함 수

전체 핵심 기능은 모든 핵심 기능이 최소 `완료 후보`이고, 모든 게이트가 통과해야만 “구현 완료 후보”로 부를 수 있다. 하나라도 `미완료`면 높은 평균과 관계없이 전체 판정은 미완료다. 외부 출시 준비 완료는 모든 핵심 기능이 `검증 완료`, 모든 기본 기능이 최소 `완료 후보`이고, 보안·개인정보·라이선스·데이터 손실을 포함한 출시 차단 문제가 없을 때만 선언한다. 의도적으로 제외한 기본 기능이 있다면 지원 범위와 사용자 안내를 명시하고 그 제외가 핵심 약속을 훼손하지 않는다는 근거를 남긴다.

## 7. 이 프로젝트에 필요한 증거

일반 기준에 더해 홈플랜 3D에서는 다음 증거를 요구한다.

- **도면 입력·보정:** 샘플 도면뿐 아니라 실제 지원 형식에서 벽·방·문·창과 mm 축척을 확인한다.
- **CV/AI 변환:** 개발 데이터와 분리한 대표 홀드아웃에서 정확도뿐 아니라 치명적인 조용한 실패율, 사용자 수동 보정 횟수와 보정 시간을 측정한다. 평균만 쓰지 말고 하위 성능·실패 사례를 함께 본다.
- **2D↔3D 일관성:** 동일한 `Project` 데이터가 양쪽 뷰에서 일치하는지 수치와 실제 렌더로 확인한다. DOM 상태만으로 3D 렌더 성공을 주장하지 않는다.
- **가구 배치:** 실측 치수, 벽 스냅, 충돌, 방 경계, 회전, 설치 높이를 정상·경계 조건에서 확인한다.
- **시각 기능:** 실제 브라우저에서 스크린샷 또는 픽셀 근거와 콘솔 오류를 함께 확인한다. 한 카메라·한 해상도만으로 호환성을 일반화하지 않는다.
- **저장·복구:** 새 프로젝트, 자동 저장, 재열기, Undo/Redo, 가져오기·내보내기를 왕복 검증하고 프로젝트 간 덮어쓰기가 없는지 확인한다.
- **외부 서비스·모델:** 인증 오류, 한도 초과, 타임아웃, 오프라인·폴백을 검증한다. 조건부로 건너뛴 테스트는 통과로 세지 않는다.
- **사용성:** `docs/USER-VALIDATION.md`의 대상 사용자 과업으로 완료 시간, 힌트 수, 수동 보정, 중도 포기를 관찰한다.
- **라이선스:** 상업 출시 판단에서는 코드·데이터·가중치의 라이선스를 각각 확인한다.

현재 알려진 CV 지표나 과거 테스트 수는 최신 리뷰의 입력 자료일 뿐 영구 합격선이 아니다. 관련 코드·데이터·환경이 바뀌면 영향을 받는 증거를 다시 실행한다.

## 8. 리뷰 절차

1. 리뷰 범위와 기준점을 고정한다.
2. 사용자 결과 단위로 기능을 나누고 핵심·기본·확장으로 분류한다.
3. 각 핵심·기본 기능의 수용 계약과 중요도를 먼저 기록한다.
4. 코드·문서·테스트를 연결한 증거 지도를 만든다.
5. 위험이 큰 정상 경로와 필수 게이트부터 실제로 실행한다.
6. 차원별 원점수와 증거 수준을 별도로 매기고 유효 점수를 계산한다.
7. 평균, 최약 기능, 게이트 실패, 미확인과 반증을 함께 판정한다.
8. 기계적 점수와 Codex 판단이 다르면 더 보수적인 결론을 기본으로 하고 차이와 이유를 기록한다.

리뷰 규모는 위험에 비례해 조절할 수 있지만, 핵심 기능 리뷰에서 1~3단계와 필수 게이트를 생략할 수는 없다. 빠른 리뷰라서 검증을 생략했다면 완료 판정 대신 잠정 판정과 미확인 범위를 낸다.

## 9. 표준 보고 형식

```markdown
# 핵심·기본 기능 완성도 리뷰

- 기준점: <commit / 날짜 / 환경>
- 대상 사용자와 결과: <한 문장>
- 범위 / 제외: <검증한 것 / 의도적으로 제외한 것>
- 최종 판정: <미완료 | 부분 구현 | 제한적 사용 가능 | 완료 후보 | 검증 완료>
- 핵심 지수 / 기본 지수: <N/100> / <N/100>
- 최약 핵심 기능: <기능, 점수, 상태>
- 게이트: <통과 N / 실패 N / 미확인 N>

| 기능 | 분류 | 중요도 | 점수 | E3+ 검증 | 게이트 | 상태 | 핵심 증거·반증 |

## 핵심 기능별 산출 근거

| 차원 | 가중치 | 원점수(0~4) | 증거 수준 | 유효 기여점수 | 증거·반증 |
```

## 10. 비판 검토 이력

### 1차 검토: 측정 타당성과 점수 왜곡

초안의 가장 큰 위험은 가중 평균이 치명적인 구멍을 숨기고, 테스트 개수나 구현 체크가 성과처럼 보이게 만드는 것이었다. 이를 보완하기 위해 다음을 반영했다.

- 사용자 결과 단위의 기능 정의와 사전 수용 계약을 추가했다.
- 점수와 독립적인 필수 게이트, 최약 핵심 기능 공개, 전체 판정 상한을 추가했다.
- 코드 존재·체크박스·테스트 개수만으로 점수를 얻지 못하도록 증거 수준과 계수를 도입했다.
- 미확인을 실패와 구분해 공개하되 점수에는 반영하지 않도록 했다.
- 핵심과 기본 점수를 분리해 많은 기본 기능이 빠진 핵심 기능을 가리지 못하게 했다.

잔여 한계: 가중치와 0~4 평점에는 여전히 리뷰어 판단이 들어간다. 따라서 원점수, 증거 수준, 반증과 이탈 이유를 함께 공개해야 하며 숫자를 객관적 진실처럼 해석하면 안 된다.

### 2차 검토: 실제 제품 타당성, 운영 비용과 기준의 경직성

수정안도 자동 테스트가 많은 기능을 과대평가하고, AI/CV의 평균 지표가 실패의 사용자 비용을 숨기며, 정교한 절차가 소규모 리뷰에는 과도할 위험이 있었다. 이를 보완하기 위해 다음을 반영했다.

- `완료 후보`와 대표 환경·사용자 근거가 필요한 `검증 완료`를 분리했다.
- 확률적 변환에는 홀드아웃, 하위 성능, 조용한 실패, 수동 보정 횟수·시간을 요구했다.
- 3D 시각 결과, 상태 보존, 외부 서비스 실패 등 증거가 주장과 직접 대응하도록 프로젝트별 요구사항을 추가했다.
- 빠른 리뷰는 범위를 축소할 수 있지만 미검증 상태에서 완료를 선언할 수 없도록 했다.
- 증거에 커밋·날짜·환경을 붙이고 관련 변경 뒤에는 재검증하도록 했다.
- 차원별 원점수·증거 계수·기여점수를 공개해 최종 숫자를 다시 계산할 수 있도록 했다.
- 문서를 기계적 판정기가 아니라 기준선으로 두고, Codex가 더 타당한 판단을 우선하되 이탈 근거를 남기도록 명시했다.

잔여 한계: 실제 사용자 검증이 없으면 사용성·가치 판단은 끝내 잠정적이다. 또한 문턱값은 제품 약속과 실패 비용에 따라 사전에 정해야 하며, 이 문서 하나가 적절한 임계값을 대신 결정해 주지는 않는다.
