자동 완성으로 부르지 않는 이유

홀드아웃 지표에서 방 추출은 사람 검토를 제거할 수준이 아닙니다. 제품은 결과를 초안으로 표시하고 벽·방·개구부·치수의 확인을 사용자의 명시적 단계로 유지합니다.

02

Placement & attachment

선택, 배치, 연결과 가격은 하나의 피드백 루프로 움직입니다.

A
카탈로그 항목 선택

pending placement 동안 기존 소파·주방 등 다른 객체 선택은 잠깁니다. Esc로 취소하면 자유 선택으로 돌아갑니다.

UX invariant

선택 의도 보존

B
배치 후보 탐색

floor·wall·surface mount와 room/충돌 조건을 검사합니다. 수전은 싱크·하부장 capability를 가진 support chain을 찾습니다.

Feedback

ghost + valid/invalid state

C
확정·Attach

유효 위치를 커밋하고 surface 제품은 supportPlacementId로 연결합니다.

Transaction

Undo/Redo + autosave

D
이동·회전·Detach

부모 이동은 자식에게 전파되며 Inspector에서 분리 후 새로운 surface를 찾거나 자유 이동할 수 있습니다.

Controls

drag · R · Shift+R · detach

E
견적 즉시 재계산

객체 추가·삭제 뒤 현재 placements를 기준으로 가격 합계와 미가격 항목을 다시 계산합니다.

Output

live cost report

수전 → 싱크대 → 하부장은 시각적 겹침이 아니라 설치 계약으로 연결됩니다.

03

Catalog data workflow

사이트별 DOM을 제품 내부 모델로 직접 끌고 오지 않습니다.

IKEA 데이터를 기준으로 정의한 HomePlan Catalog Protocol 1.0이 중간 계약입니다. 한샘·리바트 전용 sheet preset과 web override는 출처별 차이를 이 경계 앞에서 흡수합니다.

Web HTML + override↘homeplan.catalog / 1.0→schema + semantic validation→Product[]→left catalog
CSV / XLSX + brand preset↗provenance · dims · price · taxonomy · installation
단계 보존하는 정보 차단 조건
Extract provider, external ID, source URL, retrievedAt 식별자·출처 누락
Normalize mm 치수, KRW 가격, taxonomy, tags, variants 음수·비정상 치수, 지원하지 않는 version
Installation provides, requires all/any, scope, supportedBy, anchor surface인데 support capability 없음
Import catalog metadata를 Product에 유지 중복·치명 오류는 import 거부, 경고는 보고

표준의 현재 범위

이 규격은 공개 산업 표준이 아니라 이 저장소에서 검증되는 버전형 상호운용 계약입니다. 국내 사이트 “대부분”을 지원한다는 주장은 실제 adapter coverage와 표본 검증이 쌓일 때까지 보류해야 합니다.

04

Persistence & round-trip

자동 저장과 파일 보관은 서로 다른 안전망입니다.

브라우저 자동 저장

  • URL workspace ID로 프로젝트 격리
  • IndexedDB에 탭 종료 후에도 보존
  • sessionStorage mirror와 폴백
  • 프로젝트 목록·생성·열기·삭제
+

JSON 내보내기 / 불러오기

  • plan과 placements 전체 왕복
  • customProducts와 review evidence 포함
  • import origin과 새 ID로 기존 프로젝트 분리
  • 장기 보관·수동 이동 수단

샘플 초기화는 “정말 샘플 초기화를 진행하시겠습니까?” 확인 뒤 실행합니다. 프로젝트 JSON import는 현재 프로젝트를 조용히 덮어쓰지 않고 별도의 프로젝트 생명주기로 진입합니다.

06

Failure & recovery

멈춤은 실패가 아니라 경계의 표현이어야 합니다.

상황 사용자에게 보이는 동작 복구
축척 미확정 Apply 비활성·검토 항목 표시 실측 입력 또는 추정 축척 명시 동의
잘못된 surface 배치 유효하지 않은 후보와 설치 조건 안내 호환 support chain 선택 또는 Esc 취소
IndexedDB 열기 실패 세션 저장으로 계속 동작 JSON export 권장; 브라우저 저장 상태 확인
외부 AI 인증·쿼터 실패 유형화한 오류 표시 설정 수정·재시도 또는 기본 브라우저 CV 사용
생성 메시 미승인 공식 이미지 투영·파라메트릭 fallback 오프라인 검역, 권리·사람 검수 후 publish
2D 화면 캡처 지원하지 않는 상태를 명시 3D 모드에서 PNG 저장
07

Critical assessment

워크플로우의 가장 약한 단계는 코드가 아니라 관찰 증거입니다.

STRONG

실패 게이트가 핵심 여정 안에 있음

축척, 잘못된 설치 의존성, 비승인 메시를 성공처럼 통과시키지 않고 사용자 흐름 안에서 멈춥니다.

GAP 01

자동화 검증이 사용자의 이해를 대신할 수 없음

E2E는 버튼이 작동함을 보이지만 초행 사용자가 힌트 없이 올바른 support를 찾고 저장 경계를 이해하는지는 입증하지 못합니다.

GAP 02

외부 카탈로그 coverage가 아직 표준의 야심보다 좁음

한샘·리바트 템플릿과 web override는 기반일 뿐, 사이트 변경 내성과 다수 브랜드의 실제 import 성공률이 축적되어야 합니다.

DECISION

다음 백로그는 반복 문제만 채택

사용자 세션·production 관찰·지원 로그에서 두 번 이상 재현되고 사용자 결과를 훼손한 문제를 우선 개발 항목으로 승격합니다.
